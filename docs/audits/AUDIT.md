## 3. Summary of Refuted or Partially Refuted Findings

1. **C1 (Firestore Rules):**
   * *Claim:* Firestore rules lack ownership checks, field validation, and allow client writes to `otp_challenges`.
   * *Status:* **PARTIALLY REFUTED.** Comprehensive rules (v2) are already present in `firestore.rules`. `otp_challenges` explicitly blocks all client reads/writes (`allow read, write: if false;`), and all collections have ownership and schema assertions. The action required is testing them against the Firebase Emulator rather than authoring from scratch.
2. **C2 (Cloud Functions OTP Security):**
   * *Claim:* Cloud Functions lack rate limits, expiry, attempt caps, or HMAC salt in Secret Manager.
   * *Status:* **REFUTED.** `functions/src/index.ts` already contains rate limits (max 5/hr), 10-minute expiry, 5 attempt caps, 15-minute lockout, and loads `OTP_SECRET` via Firebase `defineSecret`.
3. **C7 (iOS Privacy Manifest):**
   * *Claim:* iOS `PrivacyInfo.xcprivacy` and required-reason API declarations are missing.
   * *Status:* **REFUTED.** `ios/Runner/PrivacyInfo.xcprivacy` already exists and declares all required API reasons (UserDefaults, FileTimestamp, BootTime, DiskSpace) and data types.

## 4. Phase 1 - 5 Implementation Roadmap (Pending User Approval)

* **Phase 1 (Alarm Engine Reliability):** Extract `ScheduleExpander`, implement local medication cache for background isolates, fix escalation ID cancellation, add timeout latch, unify snooze with limits, deduplicate launch intents, add `flutter_timezone`, and build device verification matrix.
* **Phase 2 (Data Integrity & Safety):** Enforce state machine transitions in Firestore transactions, deterministic inventory document IDs (`inventory/{userId}_{medicationId}`), undo validation, snoozed-dose reconciliation, and paginated history queries.
* **Phase 3 (UX/UI Redesign):** Design brief, accessible alarm screen with tap alternative, modular dashboard (<300 lines per component), day-grouped history timeline with calendar heatmap, font bundling, and `TimeFormatter`.
* **Phase 4 (Security & Compliance):** Emulator test suite for rules and functions, sanitize exceptions, Play Store Data Safety & health app declarations, in-app deletion flow, and release signing.
* **Phase 5 (Code Health):** Clean dump files (`LIB.TXT`), modularize large view models/views, resolve dependency overrides, and write architecture documentation.
